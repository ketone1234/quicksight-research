# データセット設計を Copilot に頼むプロンプト

Microsoft Copilot などの生成 AI に、Quick Sight のデータソースとデータセットの設計を頼むためのプロンプト。
DB ビューの設計が終わっている前提で使う。

## 使い方

1. 「プロンプト本文」をコピーし、【】の部分を埋める（ビュー定義書などを貼る）
2. 一度にすべてを出させると途中で切れやすいので、3 回に分けて頼む（「段階を分けて頼む」を参照）
3. 貼るのは構成（ビュー名、列名、型）だけにする。実際のデータの値は貼らない

## プロンプト本文

```text
あなたは Amazon Quick Sight（旧 QuickSight）の設計に詳しいエンジニアです。
以下の目的・前提・Quick Sight の仕様・設計ルール・入力情報をもとに、Quick Sight のデータソースとデータセットを設計してください。

# 目的
- 運用者からの問い合わせ（キーはアカウント識別子）に、Quick Sight のダッシュボードで回答できるようにする
- 分析や集計はしない。アカウント識別子で絞り込んだ明細を表で見る

# 前提
- Quick Sight は Enterprise エディション、東京リージョン
- DB は Amazon RDS for PostgreSQL のリードレプリカ。Quick Sight の VPC 接続でつなぐ
- Quick Sight は DB のテーブルを直接読まず、Quick Sight 用のスキーマにある公開用ビューだけを読む
- DB の構成:【1 つの DB か、複数の DB に分かれているか】
- DB ユーザーは 2 つ
  - SPICE への取り込み用（1 日 1 回、全件を読む）
  - 直接クエリ用（画面の表示のたびに問い合わせる）
- DB の認証情報は Secrets Manager に置く（DB ユーザーごとに 1 つ）
- 利用者
  - ビジネス部門: Reader。SPICE のデータだけを見る
  - 開発部門: Reader または Author。SPICE に加え、直接クエリのデータも見る
- Quick Sight のグループ: ビジネス部門用 business-readers、開発部門用 dev-members
- CSV と Excel のダウンロードは制限しない
- 行レベルセキュリティ（RLS）は【使わない / 使う（絞る単位:    ）】

# Quick Sight の仕様（設計で考慮すること）
- データソースは 1 つの DB にしかつながらない。DB が分かれている場合は、DB ごとにデータソースを作る
- 取り込み用と直接クエリ用で DB ユーザーが違うので、データソースも用途ごとに分ける（DB の数 × 2）
- データソースの認証情報に Secrets Manager を使う場合は、CLI か API で作る（画面からは選べない）
- データセットのクエリモードは 1 つだけ（SPICE か直接クエリ）
- 直接クエリで結合できるのは、同じデータソースのテーブルやビューどうしだけ。異なるデータソースの結合には SPICE が要る
- 2025-10 以降の新しいデータ準備画面は、データセットパラメータに対応していない
- SPICE の上限は、1 データセットあたり 20 億行または 2TB、2,000 列。文字列は 1 フィールド 2,047 文字（新しい画面では 65,534 文字）
- SPICE の取り込みスケジュールは 1 データセットに 5 つまで。指定時刻から 10 分以内に始まる
- 1 つのダッシュボードに入れられるデータセットは 50 まで、シートは 20 枚まで
- データセットの権限は User（分析を作れる）と Owner（編集や共有もできる）の 2 段階
- データソースを使ってデータセットを作るには、データソースの利用権限（PassDataSource）が要る
- RLS を使う場合、ルールのない利用者には 1 行も見えない。データセットの所有者には効かない

# 設計ルール
- ビューの列名はそのまま使い、画面に出す名前（表示名）はデータセットで付ける【付けない場合は記入】
- 1 つのビューにつき、SPICE 版と直接クエリ版のデータセットを 1 つずつ作る
- アカウント識別子の列がないビューは、次のどちらにするかを、理由を付けて提案する
  - 同じ DB の、アカウント識別子を持つビューと結合したデータセットにする
  - 画面に、別の識別子を入れる 2 つ目の入力欄を置く
- SPICE の取り込み時刻は【例: 毎日 3:00】。データセットが多い場合は、DB の負荷を考えて時刻をずらす案を出す
- データソースとデータセットの名前の付け方を提案する（DB、ビュー、クエリモードが名前から分かるように）
- 取り込みに失敗したら、所有者にメールで通知する

# 入力情報
## A. ビュー定義書（ビュー名、列名、型、意味）
【貼る】
## B. DB の一覧（どのサービスの DB か）
【貼る】
## C. ビューごとのアカウント識別子の列。アカウント識別子がないビューは、ほかのビューとつながる列
【貼る】
## D. 画面に出したい列と、その順番（分かる範囲で）
【貼る】
## E. ビューごとの件数の目安
【貼る】

# 出力してほしいもの（この順に、表とコードブロックで）
1. データソースの一覧: 名前、DB、用途（取り込み / 直接クエリ）、DB ユーザー、共有先と権限
2. データセットの一覧: 名前、元のビュー、データソース、クエリモード、共有先と権限
3. アカウント識別子がないビューの扱い: 結合する場合は結合の種類・キー・結合後の列、しない場合は画面での代わりの方法
4. 列の設定: データセットごとに、元の列名、表示名、型、画面に出すかどうか
5. 取り込みの設定（SPICE 版）: 時刻、頻度、失敗時の通知
6. 作成手順: コンソールでの手順と、CLI で作る場合の JSON の最小例（データソースとデータセット）
7. SPICE の容量の見積もり（件数の目安から）
8. 前提を置いた点と、こちらに確認が必要な点の一覧

# 注意
- 入力情報が足りない場合は、推測で埋めずに出力 8 に書いてください
- 入力情報にないビューや列を作らないでください
```

## 段階を分けて頼む

1. 本文の最後に「まず出力 1・2・3・8 だけを出してください」と足して送る
2. 一覧と結合の扱いを確認し、「次の点を直したうえで、出力 4 と 5 を出してください：【直す点】」と送る
3. 「出力 6 と 7 を出してください」と送る

## 頼む前にそろえる情報・決めておくこと

| #  | 情報                                             | なぜ要るか                                             |
| -- | ------------------------------------------------ | ------------------------------------------------------ |
| 1  | ビュー定義書（入力 A）                           | 設計の土台                                             |
| 2  | DB の一覧（入力 B）                              | データソースの数を決める                               |
| 3  | アカウント識別子の列と、つながる列（入力 C）     | アカウント識別子で絞り込めないビューの扱いを決める     |
| 4  | 画面に出したい列と順番（入力 D）                 | 表示名と列の並びを決める                               |
| 5  | ビューごとの件数の目安（入力 E）                 | SPICE の容量と取り込み時間の見積もり                   |
| 6  | RLS を使うか、使うなら絞る単位                   | ルール用のデータセットが要るかが変わる                 |
| 7  | 表示名を付けるか（元の列名のままにするか）       | 列の設定の量が変わる                                   |
| 8  | SPICE の取り込み時刻                             | DB の負荷が低い時間帯にする                            |
