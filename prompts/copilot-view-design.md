# DB ビュー設計を Copilot に頼むプロンプト

Microsoft Copilot などの生成 AI に、Quick Sight から読む DB ビューの設計を頼むためのプロンプト。

## 使い方

1. 「プロンプト本文」をコピーし、【】の部分をテーブル構成と使うデータで埋める
2. 一度にすべてを出させると途中で切れやすいので、3 回に分けて頼む（「段階を分けて頼む」を参照）
3. 貼るのはテーブルの構成（列名や型）だけにする。実際のデータの値（電話番号など）は貼らない

## プロンプト本文

```text
あなたは PostgreSQL と BI ツール（Amazon Quick Sight）のデータ設計に詳しいエンジニアです。
以下の目的・前提・設計ルール・入力情報をもとに、Quick Sight から読む DB ビューを設計してください。

# 目的
- 運用者からの問い合わせ（キーはアカウント識別子）に、ビジネス部門が Quick Sight のダッシュボードで自分で回答できるようにする
- 複数サービスのデータを横断して、推移や件数を集計・可視化する

# 前提
- DB は Amazon RDS for PostgreSQL（バージョン:【記入】）。Quick Sight は既存のリードレプリカに接続する
- ビューの作成と GRANT はプライマリで行う（リードレプリカに自動で反映される）
- Quick Sight からは元のテーブルを直接読ませず、ビューだけを読ませる
- ビューは Quick Sight 用のスキーマ【スキーマ名。例: inquiry】にまとめる
- Quick Sight 用の DB ユーザーは 2 つ
  - qs_spice_ro: Quick Sight の SPICE への取り込み用（1 日 1 回、全件を読む）
  - qs_direct_ro: 開発部門の直接クエリ用（画面の表示のたびに問い合わせる）
- どちらの DB ユーザーにも、ビューへの SELECT だけを付ける。元のテーブルの権限は付けない
- 複数のサービスが、同じ構成のテーブル（ユーザー、オーダー履歴、オーダー予約、契約状態）を持つ。サービスによって結合キーが違う

# 作るビューの種類
1. 公開用ビュー: テーブルごとに 1 つ。個人情報の列を除く。問い合わせに使う
2. 縦持ちのビュー: プラン（容量など）ごとに列が分かれたステータスを、プランを行に展開する
3. サービス横断のビュー: 同じ構成のテーブルを UNION ALL でまとめ、サービス名の列を足す

# 設計ルール
- 個人情報の列（電話番号とそのハッシュ、ほかに【あれば記入】）は、どのビューにも含めない
- 縦持ちとサービス横断のビューは、元のテーブルではなく公開用ビューを元にして作る
- アカウント識別子は、全ビューで同じ列名（account_id）・文字列型にそろえ、先頭の列にする
- 19 桁を超える数値になりうる ID は文字列型にする
- 取り込み時刻の列 extracted_at（CURRENT_TIMESTAMP）を入れる
- 問い合わせ用のビューは明細のままにする（集計、DISTINCT、LIMIT を入れない）
- サービスごとに違う結合キーは、ビューの中で共通の列名にそろえる
- 日時の列のタイムゾーンは【UTC / JST】。必要ならビューで変換する
- コード値は【そのまま出す / 名称に変換する（コードの意味は入力情報 G に貼る）】
- 命名: 問い合わせ用は v_inq_<種別>、分析用は v_<内容>【変える場合は記入】
- 期間の絞り込みは【しない / 直近〇日など】
- PostgreSQL の CREATE OR REPLACE VIEW では、列の削除や型・名前の変更ができない。この点を踏まえた変更手順も書く

# 入力情報
## A. テーブル定義
【テーブル名、列名、型、主キー、どのサービスのテーブルか】
## B. 問い合わせの種別と、種別ごとに使うテーブルと列
【記入】
## C. 分析で見たいもの
【例: プラン別のオーダー件数の推移、予約から実行までの日数、処理ステータス別の件数、契約状態・製品別の契約者数と解約の推移】
## D. サービスごとの結合キー
【例: サービス A は account_id、サービス B は xxx_id】
## E. 縦持ちにする列と、プランの一覧
【記入】
## F. テーブルごとの件数の目安と増え方
【記入】
## G. コード値の意味（名称に変換する場合だけ）
【記入】

# 出力してほしいもの（この順に、表とコードブロックで）
1. 列の公開可否表: 全テーブルの全列について、公開か非公開かと、その理由
2. ビュー一覧: ビュー名、種類、用途、元にするテーブルまたはビュー、1 行が何を表すか
3. ビュー定義書: ビューごとに、列名、型、元の列、変換内容、意味
4. DDL: スキーマの作成、CREATE VIEW、COMMENT ON（ビューと列の説明）、GRANT、ALTER DEFAULT PRIVILEGES、元に戻す SQL
5. テスト用の SQL
   - 禁止列がスキーマ内にないこと（information_schema.columns で確認）
   - DB ユーザーが元のテーブルを読めないこと（has_table_privilege で確認）
   - 元のテーブルとビューの件数が一致すること
   - 縦持ち・サービス横断のビューの件数が想定どおりであること
6. 性能の確認ポイント: アカウント識別子で絞り込む SQL の例と、元のテーブルに必要なインデックスの候補
7. 前提を置いた点と、こちらに確認が必要な点の一覧

# 注意
- 入力情報が足りない場合は、推測で埋めずに出力 7 に書いてください
- 入力情報にないテーブルや列を作らないでください
```

## 段階を分けて頼む

1. 本文の最後に「まず出力 1・2・7 だけを出してください」と足して送る
2. 公開可否表とビュー一覧を確認し、「次の点を直したうえで、出力 3 と 4 を出してください：【直す点】」と送る
3. 「出力 5 と 6 を出してください」と送る

## 頼む前にそろえる情報・決めておくこと

| #  | 情報                                                               | なぜ要るか                                                 |
| -- | ------------------------------------------------------------------ | ---------------------------------------------------------- |
| 1  | テーブル定義と、使うデータ（入力 A・B）                            | 設計の土台                                                 |
| 2  | サービスごとの結合キー（入力 D）                                   | サービス横断のビューで列名をそろえるため                   |
| 3  | 縦持ちにする列とプランの一覧（入力 E）                             | 縦持ちのビューを作るため                                   |
| 4  | 分析で見たいもの（入力 C）                                         | 分析用のビューの形を決めるため                             |
| 5  | 電話番号とハッシュ以外の個人情報（氏名、メールアドレスなど）の扱い | 公開可否表の判断基準。決めないと判断がぶれる               |
| 6  | 日時の列のタイムゾーン                                             | 日ごと・月ごとの集計がずれるのを防ぐ                       |
| 7  | コード値を名称に変換するか、その対応表                             | 画面で意味が分かるようにするか                             |
| 8  | 期間で絞り込むか（全期間か、直近〇日か）                           | データ量、SPICE の容量、表示の速さ                          |
| 9  | RLS で絞る単位（部門、サービスなど）                               | 絞り込みに使う列をビューに持たせる必要がある               |
| 10 | 件数の目安と増え方（入力 F）                                       | 性能と SPICE の容量の見積もり                              |
| 11 | PostgreSQL のバージョン                                            | 使える構文の確認                                           |
| 12 | 縦持ち・横断を DB ビューで作ること、DB ユーザーを 2 つに分けること | プロンプトの前提にしている。チームの合意を確かめておく     |
